## Fixed

- A START soon after STOP connects again when no script run handled the STOP in between, as happens while an `on_change` callback is still running or while the previous START is still waiting on ICE gathering (which takes seconds when a STUN or TURN server is unreachable). The previous session's SDP answer went to the new offer, so the new connection never completed, and a worker still being created at the STOP was attached anyway and kept its tracks, sinks included, running until the next STOP.
